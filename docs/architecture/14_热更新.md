# 热更新设计

> 版本：1.0
> 日期：2026-10-10
> 关联文档：[总体架构概览](00_总体架构概览.md)、[资源管理](04_资源管理.md)、[平台适配](11_平台适配.md)
> 模块性质：**独立可选模块**，不与基础核心强绑定；仅在项目确认需要时接入

---

## 1. 模块定位与约束

热更新属于**平台/产品能力**，设计原则：

1. **不污染通用核心**：热更新模块独立于基础框架，通过接口依赖 AssetService / PlatformService，业务代码不感知热更新细节
2. **仅原生平台需要**：Web 平台刷新即最新，无需热更新；Steam 版本优先使用 Steam 内容分发系统
3. **审核合规优先**：Android 各渠道对热更新有不同政策，接入前必须确认目标渠道允许；Google Play 对热更新代码有严格限制，通常只允许资源/脚本（已编译）更新
4. **可跳过、可回滚**：热更新失败不应阻塞游戏启动，必须提供回滚到上一个稳定版本的能力

## 2. 方案对比分析

### 2.1 候选方案

| 方案 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| A. Cocos 官方 Assets Manager 热更新 | 基于 manifest.json 的版本对比 + 差异下载，官方内置能力 | 官方支持、文档完善、与 Asset Bundle 天然兼容 | manifest 生成需手动/脚本维护；服务器需自建版本文件分发 |
| B. 自研热更新（版本文件 + 自定义下载） | 自定义版本清单、HTTP 下载、自管理文件校验 | 完全可控、可定制灰度策略 | 开发量大、坑多（断点续传、校验、回滚），重复造轮子 |
| C. 第三方方案（如 ccc-tnt-framework 热更新模块） | 开源框架的热更新模块 | 现成实现、社区维护 | 需审查代码质量、许可证、Creator 版本兼容性；维护状态不确定 |
| D. 不做热更新，全量发版 | 版本更新走应用商店/Steam | 零开发成本、零合规风险 | 更新周期长、大版本更新流失用户 |

### 2.2 推荐方案

**推荐方案 A（Cocos 官方 Assets Manager 热更新），并保持接口抽象以便未来替换为方案 B/C：**

1. 官方能力成熟度最高，与框架的 AssetService（Asset Manager / Bundle）体系一致
2. 通过 `IHotUpdateService` 接口隔离实现，未来切换自研或第三方时业务层零改动
3. 参考方案 C 的模块清单（版本检查、断点续传、失败回滚）作为设计输入，但不直接引入其代码

### 2.3 平台适用性决策

| 平台 | 是否热更新 | 方式 |
|------|-----------|------|
| Android（国内渠道） | 视渠道政策 | Assets Manager 热更新（资源+脚本） |
| Android（Google Play） | 谨慎评估 | 仅资源更新；脚本热更违反 Play 政策风险高 |
| Steam | **不推荐** | 优先使用 Steam 内容分发（Depot 更新），Steam 自动处理 |
| 桌面（非 Steam 发行渠道） | 视发行方式 | Assets Manager 热更新 |
| Web | 不需要 | 浏览器缓存策略即可 |

## 3. 接口定义

```typescript
export interface IHotUpdateService {
  checkUpdate(): Promise<UpdateCheckResult>;
  startUpdate(): Promise<void>;
  pauseUpdate(): void;
  resumeUpdate(): Promise<void>;
  cancelUpdate(): Promise<void>;
  applyUpdate(): void;                       // 重启进入新版本
  rollback(): Promise<boolean>;              // 回滚到上一稳定版本
  getUpdateState(): HotUpdateState;
  getUpdateProgress(): UpdateProgress;
  getVersionInfo(): VersionInfo;
  onStateChange(handler: (state: HotUpdateState) => void): void;
  offStateChange(handler: (state: HotUpdateState) => void): void;
}

export interface UpdateCheckResult {
  hasUpdate: boolean;
  isForceUpdate: boolean;      // 强制更新：不更新不能进入游戏
  remoteVersion: string;
  localVersion: string;
  updateSizeBytes: number;     // 预估下载大小
  updateNotes: string;         // 更新说明（本地化后显示）
  minSupportedVersion: string; // 低于此版本必须强更（由服务端下发）
}

export interface UpdateProgress {
  state: HotUpdateState;
  downloadedBytes: number;
  totalBytes: number;
  fileIndex: number;
  totalFiles: number;
  currentFile: string;
  speedBytesPerSec: number;
}

export interface VersionInfo {
  localVersion: string;
  manifestVersion: string;
  lastUpdated: number;
}

export enum HotUpdateState {
  Idle = 'Idle',                     // 空闲
  Checking = 'Checking',             // 正在检查版本
  Available = 'Available',           // 有更新，待用户确认
  Downloading = 'Downloading',       // 下载中
  Paused = 'Paused',                 // 下载暂停
  Verifying = 'Verifying',           // 校验文件
  Patching = 'Patching',             // 合并/覆盖文件
  ReadyToRestart = 'ReadyToRestart', // 待重启生效
  UpToDate = 'UpToDate',             // 已是最新
  Failed = 'Failed',                 // 失败
  RolledBack = 'RolledBack',         // 已回滚
}
```

## 5. 热更新流程设计

### 5.1 完整流程

```
游戏启动（Boot 场景）
│
├── 1. 基础服务初始化（Logger → Config → SaveService ...）
│      ※ 热更新检查在基础服务就绪后、进入主场景前执行
│
├── 2. checkUpdate()
│   ├── 读取本地 manifest（storagePath/project.manifest）
│   ├── 下载远程 manifest（manifestUrl，带时间戳防缓存）
│   ├── 对比版本号
│   ├── 无更新 → 状态 UpToDate → 继续正常启动
│   └── 有更新
│       ├── isForceUpdate=true → 强制更新流程（不可跳过）
│       └── isForceUpdate=false → 弹窗询问用户（可跳过）
│
├── 3. startUpdate()
│   ├── 创建/清理临时目录（storagePath/hotupdate_temp）
│   ├── assetsManager 下载差异文件
│   │   ├── onProgress → 更新进度（已下载/总量/速度）
│   │   ├── 网络中断 → pause → 自动 retry（≤3次）→ 仍失败则 Failed
│   │   └── 磁盘空间不足 → 提前检查，不足则提示用户清理
│   └── 下载完成 → Verifying
│
├── 4. Verifying
│   ├── 逐文件校验 md5（manifest 中记录）
│   ├── 校验失败 → 删除该文件重新下载（≤2次）
│   └── 校验通过 → Patching
│
├── 5. Patching
│   ├── 将临时目录文件移动到正式热更目录
│   ├── 更新本地 manifest 版本号
│   └── 完成 → ReadyToRestart
│
├── 6. applyUpdate()
│   ├── 修改引擎 searchPaths，热更目录置前
│   └── 重启游戏（director.loadScene('Boot') 或 game.restart）
│
└── 7. 用户选择"跳过"（非强更）
    └── 使用当前版本进入游戏，下次启动再询问
```

### 5.2 回滚流程

```
rollback()
├── 触发条件：
│   ├── 新版本启动后初始化失败（GameBootstrap 检测到关键步骤失败）
│   ├── 新版本资源加载大量失败（AssetService 错误率超阈值）
│   └── 用户主动触发（DebugPanel / 隐藏入口）
├── 执行：
│   ├── 读取备份的上一版本 manifest（storagePath/backup/）
│   ├── 将热更目录回滚到备份状态
│   ├── 清空本地版本记录
│   └── 重启游戏
└── 防循环：回滚后记录 rolledBackFromVersion，
    同一版本热更失败 2 次后，7 天内不再自动提示该版本更新
```

### 5.3 断点续传

- assetsManager 原生支持文件级断点（已下载完成的文件跳过）
- 暂停/恢复通过 pauseUpdate/resumeUpdate 实现
- 单文件下载中断时重新下载该文件（manifest 按 md5 判断是否完整）

## 6. 版本与 Manifest 设计

### 6.1 Manifest 结构

```json
{
  "version": "1.2.3",
  "engineVersion": "3.8.8",
  "minSupportedVersion": "1.0.0",
  "forceUpdate": false,
  "packageUrl": "https://cdn.example.com/hotupdate/1.2.3/",
  "remoteManifestUrl": "https://cdn.example.com/hotupdate/project.manifest",
  "remoteVersionUrl": "https://cdn.example.com/hotupdate/version.manifest",
  "updateNotes": {
    "zh": "新增第二章剧情，修复已知问题",
    "en": "Chapter 2 added, bug fixes"
  },
  "searchPaths": [],
  "assets": {
    "bundles/chapter_01/import/xxx.json": {
      "size": 10240,
      "md5": "a1b2c3d4..."
    }
  }
}
```

### 6.2 版本号规则

- 采用三段式：`主版本.次版本.修订号`（如 1.2.3）
- 主版本/次版本：功能迭代，对应应用商店发版
- 修订号：热更新递增，仅通过热更通道分发
- `minSupportedVersion`：服务端下发，低于此版本强制更新（用于紧急修复）

### 6.3 服务端文件组织

```
hotupdate/
├── project.manifest          ← 指向最新版本（小文件，先下载）
├── version.manifest          ← 轻量版本信息（版本号、强更标记、更新说明）
└── 1.2.3/
    ├── project.manifest      ← 1.2.3 完整文件清单
    └── ...资源文件...
```

- version.manifest 只含版本号和强更标记，用于快速检查
- project.manifest 含完整文件清单和 md5，确认更新后才下载
- CDN 需配置：manifest 文件不缓存（或短缓存），资源文件长缓存

## 7. 安全性设计

| 项目 | 措施 |
|------|------|
| 下载校验 | 每个文件按 manifest 中 md5 校验，失败重下 |
| 传输安全 | 强制 HTTPS；manifest 可选签名校验（防止 CDN 被劫持后下发恶意 manifest） |
| 路径安全 | 下载文件名由 manifest 定义，禁止 `../` 等路径穿越；存储目录由平台 Adapter 提供固定路径 |
| 版本安全 | `minSupportedVersion` 由服务端控制，防止旧版本漏洞无法收敛 |
| 回滚保护 | 每次热更成功前备份上一版本 manifest，回滚可用 |
| 失败保护 | 热更失败不阻塞启动；同一版本反复失败进入冷却期 |

## 8. 与现有模块的关系

| 模块 | 关系 |
|------|------|
| GameBootstrap | 在基础服务初始化完成后、进入 Main 前调用热更新检查；热更失败不阻塞启动（非强更时） |
| PlatformService | 新增 `getHotUpdateAdapter()` 能力，由平台决定热更实现；storagePath 由平台 Adapter 提供 |
| AssetService | 热更完成后通过 searchPaths 使 AssetService 优先加载热更目录中的 Bundle；AssetService 不感知热更 |
| SaveService | 热更不触碰存档数据；但新版本可能伴随存档迁移（已有 schemaVersion 机制覆盖） |
| EventBus | 新增 `HotUpdateStateChanged` 事件，UI（更新弹窗、进度条）通过事件驱动 |
| SceneService | 强更流程在 Boot 场景内完成，不涉及场景切换；热更完成后 applyUpdate 重启到 Boot |
| DebugPanel | 新增热更分区：当前版本、远程版本、强制更新、回滚按钮 |

## 9. UI 流程设计

| 场景 | UI 表现 |
|------|---------|
| 检查中 | Loading 遮罩，显示"检查更新..."（超时 5s 视为无更新，继续启动） |
| 非强更弹窗 | 显示版本号、更新大小、更新说明；按钮：立即更新 / 下次再说 |
| 强更弹窗 | 显示更新说明；按钮：立即更新（无跳过选项）；点关闭则退出游戏 |
| 下载中 | 进度条 + 百分比 + 已下载/总量 + 速度；可暂停/取消（非强更） |
| 下载失败 | 提示网络问题；按钮：重试 / 稍后（非强则稍后可进游戏） |
| 空间不足 | 提示需要 X MB 空间，引导用户清理 |
| 校验中 | Loading 遮罩，"校验文件完整性..." |
| 待重启 | 提示"更新完成，即将重启"；1s 后自动 applyUpdate |

## 10. 错误处理

| 场景 | 处理方式 | 状态 |
|------|---------|------|
| 远程 manifest 下载失败（网络） | 重试 ≤3 次，仍失败视为无更新继续启动 | UpToDate |
| 版本检查超时（5s） | 视为无更新，继续启动 | UpToDate |
| 文件下载失败 | 重试 ≤3 次；仍失败→Failed，非强更可跳过进游戏 | Failed |
| md5 校验失败 | 删除重下 ≤2 次；仍失败→Failed | Failed |
| 磁盘空间不足 | 开始下载前预检查；不足则提示用户 | Failed |
| 新版本启动后初始化失败 | 自动回滚到上一版本（防循环冷却） | RolledBack |
| 热更中应用被杀（Android） | 下次启动重新检查，已下载文件按 md5 复用（断点续传） | - |
| CDN 故障 | 灰度期间保留多 CDN 源，manifest 支持多 packageUrl 备选 | - |

## 11. 发布与运维流程

### 11.1 热更包发布流程

1. Creator 构建原生工程后，运行 manifest 生成脚本（扫描构建产物生成 assets + md5）
2. 将资源与 manifest 上传至 CDN 对应版本目录
3. 更新根目录 `project.manifest` 指向新版本（或通过运维后台切换）
4. **灰度策略**：先放量 5% → 观察 24h（崩溃率、热更失败率）→ 50% → 100%
5. 灰度实现：version.manifest 按用户 ID 哈希/百分比下发不同版本号

### 11.2 监控指标

| 指标 | 告警阈值 |
|------|---------|
| 热更检查成功率 | < 95% |
| 热更下载成功率 | < 90% |
| 校验失败率 | > 2% |
| 新版本启动崩溃率 | 高于上一版本 50% |
| 平均下载耗时 | > 60s |

### 11.3 应急预案

- **紧急强更**：服务端将 `minSupportedVersion` 提升至当前最新版本，旧版本启动即强更
- **热更事故回退**：CDN 上将 project.manifest 回指上一版本；客户端 7 天冷却机制防止自动重试同一问题版本

## 12. 实施阶段建议

热更新**不进入 P0-P6 基础框架阶段**，作为独立阶段 P7 在框架稳定、首版玩法验证后再实施：

| 编号 | 任务 | 验收标准 |
|------|------|---------|
| P7-1 | 渠道政策确认 | 目标渠道书面确认允许热更新 |
| P7-2 | CDN 与服务端搭建 | version/project manifest 可访问，灰度开关可用 |
| P7-3 | IHotUpdateService 接口与状态机 | 接口定义评审通过 |
| P7-4 | AndroidHotUpdateAdapter 实现 | 真机检查/下载/校验/应用/回滚全流程通过 |
| P7-5 | 热更 UI（弹窗/进度条/强更） | UI 流程按第 9 节验收 |
| P7-6 | manifest 生成脚本 | 构建后一键生成 manifest + md5 |
| P7-7 | 失败/回滚演练 | 模拟 CDN 故障、md5 篡改、磁盘满、新版本崩溃回滚，全部符合第 10 节预期 |
| P7-8 | 监控接入 | 第 11.2 节指标可查、可告警 |

## 13. 实现注意事项

1. **`jsb.AssetsManager` 仅原生平台可用**：代码中必须通过平台适配器隔离，禁止在通用逻辑直接引用 `jsb` 命名空间
2. **热更目录不要与存档目录混用**：热更文件可随时被清空重建，存档必须独立存放
3. **searchPaths 修改在 game 启动早期**：applyUpdate 后必须完整重启（game.restart），不能热切 Bundle 引用
4. **不要把首包资源全部交给热更**：首包保留最小可运行内容（Boot/Loading 场景 + 核心框架），防止首次热更失败导致完全不可玩
5. **Steam 版本不做热更**：Steam 客户端有自己的更新机制，叠加热更会造成文件校验冲突
6. **时间戳防缓存**：请求 manifest URL 追加 `?t=` 时间戳，避免 CDN 缓存旧 manifest
